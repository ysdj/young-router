# Young Router Repository Guide

## Scope

- Treat `young-router` as a standalone repository. Do not inspect parent directories for repository instructions.
- Keep provider names, models, API keys, request IDs, local paths, traces, and logs out of committed files. Public examples use only neutral synthetic values.
- `config.example.yaml` is the public configuration example and must remain safe to publish.

## Source Of Truth

- `rn/packages/shared/` owns shared React/TypeScript routes, composition, interaction state, i18n, and the typed Core IPC client.
- `young_router/core/` owns domain state, validation, staged configuration, service operations, persistence, and the authenticated versioned loopback IPC contract.
- `rn/apps/macos/` is the AppKit host and `rn/apps/windows/` is the WinUI 3 host. Native code owns platform leaves: status/tray menus, windows, native controls, system WebView hosts for shared code panes, secure inputs, file panels, alerts, shortcuts, and platform lifecycle.
- One feature has one shared UI and one Core domain implementation. Do not introduce a second platform-specific domain store, configuration writer, WebView application shell, Electron/Tauri layer, or legacy shell launcher. Embedded system WebViews are permitted only for the shared code panes.
- React holds view state only. It must not write configuration files, manage the proxy process, read arbitrary paths, or handle raw credentials. Versioned code-editor document text is the explicit exception.
- The language choice belongs in each host's native application menu. Shared UI consumes that preference; do not add an in-window language selector.
- All user-visible shared strings go through i18n. Keep platform titles and menu labels aligned with the selected language.

## UI And Native Boundaries

- Preserve native platform behavior and visual conventions. Shared UI describes the workflow; native leaves render controls that require AppKit or WinUI behavior.
- Default every desktop surface to compact native density. Avoid redundant in-content titles, oversized empty cards, web-like vertical whitespace, and detached action rows; prefer tightly grouped 24–28 px controls, concise helper text, content-sized route windows, and one fixed bottom action bar. Tabs must be genuinely switchable and render only their active pane. Compact layouts must still reflow before controls overlap or hide required content on either macOS or Windows.
- A settings pane window has no route-level action footer. The shared settings shell commits its staged domains as the user edits (`IMMEDIATE_APPLY_DEBOUNCE_MS`), and its one permanently mounted bottom status strip reports the result (`common.ready` → `common.saving` → `common.saved`). File selection, import/export, WebDAV testing, and synchronization actions belong in the active pane, never in a footer.
- Every subordinate surface presents itself through one child-window contract: the provider wizard, the raw file editor, 分组管理, the relay sign-in browser, the relay usage log, the read-only document viewer, the official provider sign-in, and the model chooser each open their own movable titled window above the window they were opened from, with that window's content locked until the surface closes. The lock is `NativeChildPanelShield` — a view over the parent's content that swallows every mouse event and holds the first responder, plus the parent's disabled window buttons — and never a modal session or an attached sheet: `NSApp.runModal` freezes the React host — see the child-surface modal freeze incident — and an AppKit sheet cannot be dragged and draws no title bar. The child opens through `presentChildPanel(_:in:prepare:)`. Every dismissal path — the title-bar close button, an in-surface Close or Apply, and a resolved completion — ends the child through `endChildPanel`, which releases the lock, detaches the child window, and ends the children that child opened; a warm window is only created (`warmOnly:`) and never presented, so a surface that is not on screen never holds a lock.
- A child surface that writes behind its own Save/Close creates nothing before that Save: 添加向导's steps hold the provider's name, its address, its key, and its models, and 完成 is the wizard's one create — the provider (carrying the key the keys step typed) and its models arrive together, so 下一步 never mints a provider and a wizard closed unfinished reserves nothing. A key value may therefore be typed before the provider it belongs to exists: the wizard files it under its own token (`WIZARD_PENDING_KEY_PREFIX`, Core's `ProvidersModelsDomain._WIZARD_KEY_TARGET_PREFIX`; `provider.add`'s `pending_api_key` adopts it, and a create without it is refused), the model step lists candidates through that same token (`providers.fetch_models`' `pending_provider`, whose summary names the token), and the window that opened the wizard drops the staged value on every dismissal path (`provider.discard_pending_key`, dispatched quietly — a child's bookkeeping never reports into the pane). A provider whose sign-in needs the record it belongs to — OpenAI/Claude's device login, exactly as the pane's own 添加官方账号 — is created by the press that signs in to it, never by 下一步. `tests/test_rn_ui_parity.py::test_the_wizard_creates_nothing_before_it_finishes` and `tests/test_core_provider_wizard_staging.py` are the guards.
- Every confirmation the app asks — the shared UI's `showConfirmation` (删除供应商/模型/密钥, 放弃更改, 覆盖磁盘版本, 导入, 探测结果, 关闭窗口), the Codex catalog restart question, and the version acknowledgement — is one decision surface on each host and never an alert: `AppKitNativeLeaf.presentDecisionPanel(_:message:answers:in:locksParent:completion:)` on macOS, `WinUI3NativeLeaf::Confirm` on Windows. On macOS it is drawn the way the system draws an alert, because it *is* one of the app's dialogs and a document-style titled window for 删除供应商 reads as the wrong kind of window: a borderless rounded panel (`[.borderless]`, `isMovableByWindowBackground`, the window background at `nativeDecisionCornerRadius`), no title bar, the question in bold over its detail, and the answers as one row of equal width across the bottom.  The numbers are `NSAlert`'s own and live in the module's constants beside it — `nativeDecisionTextWidth` (220) growing to `nativeDecisionMaxTextWidth` (380), `nativeDecisionPanelInset` (20), `nativeDecisionAnswerHeight` (28) with `nativeDecisionAnswerGap` (8), and `nativeDecisionGap` (11) between question, detail, and answers — so a two-word confirmation is a 260 pt panel and a long one grows only to 420 pt. The question stays the window's own `title` for a screen reader and for the lock's accessibility label even though nothing draws it, the panel must override `canBecomeKey` (a borderless window otherwise answers no key at all), and `positionDecisionPanel(_:over:)` places it centred on the window that asked and inside that window's screen — `NSWindow.center()` leaves a borderless child wherever the screen's centre falls relative to the parent. A destructive answer draws with the system's red ink on the ordinary bezel (a plain button ignores `hasDestructiveAction` and `bezelColor`, so the ink is set explicitly) and never with the default button's accent fill, which would paint 删除 blue. A question the shared UI asks is a child surface: it locks the window that asked through `presentChildPanel(_:in:)` and ends through `endChildPanel`, so it never runs a modal session (see the child-surface modal freeze incident); a question a background event asks floats instead (`locksParent: false`, the catalog restart), because the user is not answering for a window they were working in. Return carries the primary answer and Escape, the window that asked going away, and the panel's own action all answer exactly once through `finishDecisionPanel(_:answer:)` (a borderless panel has no title-bar close button). An answer that cannot be undone is stated by its caller — `destructive` in the typed adapter, spread positionally into `showConfirmation(title:message:confirmLabel:destructive:resolve:reject:)`/`ShowConfirmation` — and drawn the platform's way (`NSButton.hasDestructiveAction`, the system critical ink on Windows); inferring it by matching a translated label is a regression, because a re-worded 删除 silently loses the mark. The same rule covers the React `DependencyPolicyDialog`, which takes `destructive` as a prop and mounts once.
- Every settings pane that renders labelled controls draws them as fields of one shared, left-aligned grid defined in `ui/YoungRouterApp.tsx`: `SETTINGS_FIELD_LEAD` (8), `SETTINGS_FIELD_LABEL_WIDTH` (128), `SETTINGS_FIELD_GAP` (6), `SETTINGS_FIELD_VALUE_WIDTH` (160), `SETTINGS_FIELD_ROUTE_WIDTH` (200, for a route name), `SETTINGS_FIELD_HELP_INDENT` (lead + label + gap = 142) and `SETTINGS_PANE_INSET` (14), plus the `SETTINGS_FIELD_LIST/FIELD/ROW/ROW_INDENTED/LABEL/VALUE_SLOT/ROUTE_SLOT/HELP_SLOT/HELP_TEXT/SWITCH_SLOT` styles they spread; general, runtime settings, backup and sync, and the external clients all use them instead of restating numbers. Labels sit left-aligned in their own column, the control column and the tips under it start at `SETTINGS_FIELD_HELP_INDENT`, and every pane body starts at `SETTINGS_PANE_INSET`; switching panes must not move a label or a control, and a pane that picks its own width or inset is a regression. A pane whose rows carry the modified marker (runtime settings) positions it inside the row lead (`runtimeModifiedBar` is absolutely positioned on the row's left edge, so it takes no space), which lands the label on the same x as `SETTINGS_FIELD_ROW_INDENTED`. One on/off setting is a `NativeToggle` switch, never a `NativeCheckbox` (the 使用漾路由 API and 漾路由模型列表 switches, the WebDAV enable switch), starting flush with the control column (`SETTINGS_FIELD_SWITCH_SLOT` carries no leading inset); only a multi-select stays checkboxes (`NativeCheckbox`, the data-management import/export section list) — the control shape follows the question it asks.
- A settings pane that splits its body into a list plus a detail renders the shared `SettingsRail` (runtime settings, backup & sync, external clients): one width, one source-list column, one row rhythm — not a per-pane list of its own. One rail selection renders one detail surface, never a continuous scroll whose position drives the selection back: the runtime settings rail swaps the pane to the selected category's own settings (the surface is keyed by the category, so a switch starts at its top), exactly as a backup tab and an external client do. A detail surface that names its selected row (runtime settings, external clients, backup & sync's tabs) renders the shared `SettingsDetailHeader` above it — one header height, one title/hint type step, one divider — with the pane's own controls on the trailing edge; the body below it opens on its content, never on a second heading that repeats the band. The rail is the sidebar's *compact* source list, so it shares the sidebar's chrome, type step, and ink while stepping one density down (sidebar 30 pt row + 2 pt spacing = 32 pt pitch, rail 26 + 2 = 28 pt pitch, the platform's own in-pane row height). A symbol-less source-list row keeps that type step and ink (`SourceListFont()`/`SourceListTitleColor` on macOS, `kSourceListFontSize` at medium weight on Windows) instead of the 13 pt regular body cell, and the host swaps the ink by hand on the emphasized selection.
- Every settings-pane window keeps one permanently mounted bottom status strip, rendered one type step below body text (`UI_TIP_FONT_SIZE`). A pane result replaces the localized idle `common.ready` (就绪) label; never mount that strip conditionally on a result, because the pane must not shift or resize whenever an action reports. That strip is the pane's *only* report surface: a write Core refused, rolled back, or could not finish states what the user can see there (`common.notApplied` 更改未生效, `common.notAppliedPartial` 部分更改未生效, `error.validationFailed` 校验未通过，更改未生效。), never as a validation card over the pane's content and never as a Core step name — a bare snake_case identifier (`relay_binding_materialization_failed`) is internal vocabulary and stays out of the strip, while the offending rows are marked in place (`alertRowKeys`). A status must name what actually refused the write, and it must never fire for a record the user has not finished: ＋ creates a *draft* model (`model.add` with `enabled: false` — a disabled model is skipped by validation and never reaches the runtime model list or a public model group, while the inspector states what is left with `providers.draftModelHint`, or `providers.draftModelKeylessHint` when there is no key to inherit).  The draft inherits the key the user is working in (`modelProviderKeyState(model)`, else the key the pane’s 获取模型 picker points at, else `providerKeyStates(provider)[0]`) and the model list groups by the key’s own slot id, drawing a group row only for a key a model actually belongs to, so ＋ files the new row inside a real key group instead of under an invented 未定义密钥 one, and a providers_models apply enters the relay transaction only when the draft actually changed relay-bound material (`_relay_binding_projection`: relay-sourced keys and the models that point at them — including the order mode each linked route follows — compared against the applied baseline), so a relay backlog states itself (`relay_not_ready`/`relay_preflight_failed` → `error.relayNotReady` 中转站还有待处理的操作，本次更改未生效…) instead of reading as 校验未通过，更改未生效。 on an edit that has nothing to do with the relay. This is the repository's reading of the standard create-then-configure shape: no premature errors for an unfinished record, and a failure that names its own cause.
One status, one place: a window never prints the same status twice at once — the provider wizard's validation/login feedback lives only in its footer line (its step bodies carry instructions, never a copy of that line), 常规's service strip names the action that landed (`service.started`/`service.restarted`) instead of repeating the 运行中 the row beside it already shows, and 分组管理's copy result takes the sheet's one status line beside its buttons instead of a second line under the detail rows. A message that talks about required fields only works when the fields wear the mark: `NativeFormRow` takes `required` and draws the `＊` at that label, and a pair that is one entry rather than two required fields says so in its own words (`providers.wizard.manualModelPairRequired`).
That strip belongs to a settings pane window only: a child window keeps no status bar of its own and states its result beside its own footer buttons — the provider wizard's footer line, the raw file editor's `editorFooterStatus`, and 分组管理's native line between its 自动分组 switch and 关闭/保存并关闭 (anchored so a message never moves a button) — while the window that opened it reports nothing about the child's work: the shell's immediate apply is gated while a child with its own save is up (`isGroupManagerOpen`, beside the wizard and editor gates), the apply a child asks for is quiet (`apply({quiet: true})`), and a 分组管理 save that failed keeps the sheet's rows and its 保存并关闭 with 更改未生效 beside those buttons instead of reaching back into the pane. A copy that worked says nothing anywhere — no 已复制 confirmation, in the panes or in the group manager — and only a failed copy takes a word.
- Use typed IPC snapshots and actions. Never expose a path, secret, or unrestricted native capability through ordinary React props. Versioned code-editor document text may flow through the shared code-editor view.
- One raw-editor document is bounded by `MAX_EDITOR_DOCUMENT_BYTES` and one Core frame by `MAX_MESSAGE_BYTES` (`young_router/core/protocol.py`), mirrored by the Windows bridge's `kMaxIpcMessageBytes` and the WinUI code editor's own gates. A read answers with the document *plus* its baseline and the editor page embeds both in its bootstrap, so the frame budget covers two documents; the managed Codex catalog this app writes for its own model list is already past 2 MB, which is why the two budgets move together. The schema's `editorParams`/`editorResult` `maxLength` values and the staged raw-document check in `ClientSettingsDomain.stage` follow the same number. A document past the cap is refused as `editor_too_large` (「文件过大，内置编辑器无法打开。」), never as `error.coreUnavailable`, so a size refusal never reads as a dead Core.
- Every `@objc` method on `AppKitNativeLeafModule` (or any `RCT_EXTERN_MODULE` class) must also be declared in `rn/apps/macos/src/native/macos/AppKitNativeLeafBridge.m` with `RCT_EXTERN_METHOD(...)`. The TurboModule interop exposes only methods listed there; an undeclared method is `undefined` in JS and `bridge.foo?.()` optional chains silently no-op with no warning or log. Always pair a new export with an assertion in `tests/test_rn_native_acceptance.py`.
- Route windows must render their first data-backed frame from the shared snapshot; do not paint empty shells and refill them or issue duplicate per-window snapshot/subscription requests.
- Secure inputs and file panels use opaque one-time native capabilities. Do not serialize secret values into IPC snapshots, logs, drafts, or test fixtures. Raw configuration documents use the authenticated versioned editor IPC instead of the retired native-only editor path.
- The settings shell is real-time: an edit is written to Core and applied without an Apply control, so pane copy never tells the user to press 应用/Apply. It states what was saved, or what still blocks the write (validation, disk conflict, a shared-revision conflict); a service reload stays a Core-side consequence of the write, never a second user action. Only the child surfaces with their own button keep staged wording: the provider wizard, the raw file editor, and 分组管理 (its footer is 关闭/保存并关闭). Adding a tip that names an Apply step for a shell pane is a regression — `tests/test_rn_ui_parity.py::test_settings_shell_copy_never_names_an_apply_action` fails on the removed Apply vocabulary and on any translated shell string that describes an Apply press.
- A native surface reports a wait in flight with the app's own busy wheel, never a progress-indicator view: `AppKitBusySpinner` owns the frames on macOS (the Fabric busy button reads them through the generated Swift header and the 分组管理 sheet turns the same ones beside 密钥), Windows keeps its platform `ProgressRing`, and the wait's words ride the wheel as its tooltip and accessibility label. The wheel swaps pre-rendered frames instead of animating a view, so nothing re-lays out while it turns.

## Runtime And Compatibility

- The runtime starts from `.litellm-runtime/config.yaml`; source configuration is validated and staged explicitly. No file mutation may silently restart the service.
- Keep proxy data-plane headers transparent. Outside an explicitly scoped compatibility hook or runtime patch, do not add, remove, rename, rewrite, normalize, mask, or impersonate request or response headers. Preserve downstream-supplied headers byte-for-byte when forwarding them upstream, including headers or values that identify LiteLLM; do not invent upstream identity headers or strip LiteLLM/SDK fingerprints merely to conceal the implementation. Every header exception must stay narrowly tied to its documented protocol or failure mode and have a focused regression test.
- Nothing this app sends may identify it. A downstream client's `User-Agent` is forwarded byte-for-byte; a request without one, and every request the app makes on its own behalf (relay dashboard calls, provider probes, usage-log reads, WebDAV, helper workers, local proxy calls), presents the shared browser identity from `young_router/browser_identity.py` instead of an app, tool, or SDK fingerprint. The native hosts pin the same literal (`RelayBrowserIdentity` on macOS, `kRelayBrowserUserAgent` on Windows) so one account keeps one fingerprint — a relay that binds a session to its IP and `User-Agent` (sub2api's session binding) revokes the session family on any mismatch. The only exception is a loopback-only control call (Core IPC, the proxy's own health endpoint), which may keep an internal marker because it never leaves the machine. `tests/test_browser_identity.py` is the guard: it compares the Python and native literals, scans shipped request code for self-naming `User-Agent` values, drives the data-plane steps, and covers the staged-package rewrite. Never add a User-Agent, product token, or `X-...` client name that names this app, its hosts, or its helper packages; when a helper package sends one of its own, normalize it in the same staging step that adapts that package.
- Every artifact-producing desktop build must update `LITELLM_VERSION` from the latest installable stable LiteLLM release on PyPI before selecting or reusing a bundled runtime and before invoking the platform build. This applies to direct macOS and Windows builds, macOS build-and-install, and release packaging. If the update cannot complete, fail the build; never silently package a stale lock. A nested build may skip only a duplicate lookup already completed successfully by the same top-level build invocation.
- Every artifact-producing desktop build must also re-check each third-party integration against its latest upstream release and adapt the repository when upstream drifted; never package a stale adaptation. `pi-web-access` (npm, `nicobailon/pi-web-access`) is staged from the npm `latest` dist-tag by `scripts/update_pi_web_access.py` on every build, so its adaptation surface is the published Pi peer graph, the staged worker smoke test, and the User-Agent normalization `_normalize_staged_user_agents` — add a missing `@earendil-works/...` package to `FALLBACK_PI_PEERS` only when that smoke test demands it, and when upstream renames or drops the self-naming `User-Agent` literals the staging step must fail loudly and be re-checked rather than silently shipping them. A release that ships a nested `node_modules` of its own (npm nests a dependency when the flat tree carries another version of it) keeps that copy exactly as published and has the peer closure merged beside it, never over it. `dsh-vision-router` (npm, `ysr666/dsh-vision-router`) is a Node/Cordis plugin that no build step fetches, so its mirrored subset — `young_router/dsh_vision_router.py`, the Vision Router entries in `young_router/core/runtime_settings_schema.py`, and the default fallback config JSON — must be re-checked against the current upstream release before builds: free OVH chain models and order, local Ollama/LM Studio defaults, and `freeFallback`/`timeoutMs`/`maxTokens`/`httpProviders` semantics. `TraceOne` (GitHub, `wangchao0708/TraceOne`) is staged from its default branch by `scripts/update_traceone.py` on every build and powers the model detail pane's degradation deep test through `young_router/traceone.py` and `young_router/traceone_worker.mjs`; its adaptation surface is the staged `dist/traceone.js` exports (`TARGET_MODELS`, `parseGridResponse`, `identifyWithArtifacts`), the `dist/data` documents the engine reads (resolved by the `schema` each declares — `robust-number-fingerprint-bank` is the `bank`, `traceone-sequence-adapter-v1` is the `adapter`, which since the 2026-10 release carries the support statistics that used to be a third document), and `prompts/identity-web-v1.txt`, which the staging script validates together with a real staged-worker smoke test — when upstream renames one of them, update the staging file list, the adapter, and the deep-test plan together.  `dsh-workbuddy-connect` (npm, `corrinehu/dsh-workbuddy-connect`) is staged from the npm `latest` dist-tag by `scripts/update_workbuddy_connect.py` on every build and powers the WorkBuddy (CN) and WorkBuddy AI (international) providers: the staged package owns the desktop-app credential format, the token refresh, both model catalogs, and the upstream Chat Completions wire format, while this repository only starts it and states its answer — `young_router/workbuddy_worker.mjs` runs one shim per variant behind a Core-owned loopback port with a bearer, `young_router/workbuddy.py` owns that worker's lifetime and the two `os.environ/` references the proxy resolves (`YOUNG_ROUTER_WORKBUDDY_BASE`/`_KEY`, `YOUNG_ROUTER_WORKBUDDY_AI_BASE`/`_KEY`), and `young_router/core/domains/providers_models.py` shapes the providers. A WorkBuddy provider is created by the provider wizard's type select as an empty service entry (its URL is the service's own address and is not editable); the desktop app's account is linked afterwards in the provider editor's one association block — the same block that a station-backed provider uses, titled 「服务商关联」 whenever the provider's address belongs to an official service (`workbuddy`, `gpt` → `openai`, `claude`). That block's 模型管理 button runs the same key-driven fetch-and-choose path as 「获取模型」 (the provider keeps its `workbuddy-local` key slot, and the loopback worker answers `/v1/models` with the desktop app's live roster), so no WorkBuddy-specific detail surface exists. Its adaptation surface is the package's published exports (`WorkBuddyCredentialStore`, `WorkBuddyUpstreamClient`, `WorkBuddyCatalog`, `createWorkBuddyShim`, `WORKBUDDY_VARIANTS`), the peer closure the staging script requires, and the worker's control routes; when upstream renames one of them, update `young_router/workbuddy_worker.mjs`, the staging requirements, and `tests/test_core_workbuddy.py` together. Never reimplement its protocol here or patch the staged package in place.
- The macOS LiteLLM proxy must run with `LITELLM_NUM_WORKERS=16`. Do not lower the default, alter it during a restart, or use a smaller worker count as a performance or recovery workaround unless the user explicitly requests that configuration change.
- Every newly created proxy process must start with empty route-recovery and deployment-cooldown runtime state. Never carry `.litellm-runtime/route-recovery-state.json` or `.litellm-runtime/deployment-cooldowns.json` across app starts, service starts, restarts, or reloads.
- Preserve LiteLLM routing, Responses stream semantics, tool ordering, IDs, explicit terminal errors, and metadata-driven compatibility bridges. Do not add request-specific or provider-specific routing hacks.
- The Core IPC schema beside the implementation is the durable contract. Update its validators, typed client, host bridges, and focused tests together when the contract changes.
- Core event delivery and the shared revision are per-window contracts: the host bridge fans one Core event stream out to every registered window module, and every host passes Core's private `--metadata` path (an unreadable file counts as absent state) so a replacement Core resumes the shared revision.
- The macOS Vision helper is built into `Contents/Resources/Core/bin/vision_ocr`. Keep its source in the RN macOS host and never restore a `Resources/App` lookup.

## Known Runtime Failure Modes

### A New Row Is Live Until It Says Otherwise (2026-10-02)

- ＋新建供应商 / ＋新建模型 used to create the row **disabled** (a draft the user had to enable by hand after filling it in).  The product rule is the opposite now: a row the user just created is enabled.
- Fix: `provider.add` carries `enabled: true`, `model.add` carries `enabled: true` (Core's own default for a create that states no flag is enabled, and a test pins that), and the pane keeps the placeholder name as the row's public name and upstream so the document stays valid while the user edits it.
- The row is not silently passed off as finished: `modelNeedsAttention` also answers a placeholder-named model, so the freshly created row draws in the pane's warning ink until the placeholder is replaced, and its inspector states what is left (`providers.draftModelHint` / `providers.draftModelKeylessHint`, reworded from "尚未启用…" to "新建的模型默认启用…").
- Deliberate difference: the routes pane's ＋ still creates a **disabled** route.  A new route joins the public-model group on screen, and enabling a row whose upstream is still the group's own name would put a placeholder into that group's live order (it takes slot 0, so it would be tried first and fail over on every request).  A model create starts a *new* group instead, which is why it can be live from the first press.
- Verified with `tests/test_core_public_models.py` (`test_a_new_provider_and_model_default_to_enabled`) and `tests/test_rn_ui_parity.py` (`test_a_new_provider_and_model_start_enabled`, plus the updated create-then-configure and zero-order guards).

### A Host Keeps One Identity And One Default (2026-10-02)

- Six host-level differences, five of them between the two platforms.
- **macOS's relay sign-in page presented the wrong browser.**  `NativeRelayLoginController` created its `WKWebView` without `customUserAgent` (only the provider-auth controller pinned `RelayBrowserIdentity.userAgent`), while its own probes, dashboard reads, and usage calls set that User-Agent.  A station that binds a session to its IP and `User-Agent` (sub2api's session binding) revoked the session the page had just created, so 登录成功 never landed while the same account worked on Windows.  Fix: the relay page pins the same literal, and `tests/test_browser_identity.py` now asserts that every remote WebView on the host sets it (and that the local read-only viewer does not need to).
- **Windows' tray left-click opened 常规.**  The default action was "the first enabled `open-` action", and the shared UI lists 常规 first, so the same gesture opened a different pane than macOS's `openNamedRoute("providers-models")`.  Fix: the tray prefers `open-providers-models` and falls back to the first route.
- **常规 was missing from the macOS status menu's route group.**  `statusMenuOrder` never named `open-general-settings`, so the item landed at the bottom beside 版本/退出 instead of with its panes; the menu also had no fallback title for it before the first Core snapshot.  Fix: the order carries it first, its fallback title comes from the shared `routeGeneralSettings` string, and the localization contract gained that key.
- **The catalog toggle showed a hard-coded English label.**  `menuFallback` returned the literal "Use LiteLLM models in Codex" until the first snapshot arrived, so a zh-Hans user saw one English item in an otherwise translated menu.  Fix: the label comes from the shared `codexModelCatalog` string.
- **A warm editor window kept the app in the Dock.**  `prepareFileEditor` registers an ordered-out `file-editor` window, and the activation policy treated any registered window as presented, so closing the settings window left a Dock icon, an app menu, and no window to click.  Fix: a window counts only while it is visible; opening the editor presents it and restores the regular policy.
- **Windows snapped the window back on every open.**  Every `OpenRoute` re-applied the route's initial content size and restored the window, so a resized or maximized window lost its geometry on the next pane switch or menu action; macOS only applies geometry when it creates a window.  Fix: the host's one window takes the initial size of the route that opened it, once, and only an iconic window is restored.
- Known limit: Windows has no relay usage-log surface at all — `openRelayLogs` is optional in the bridge, and the shared 在线用量 tab walks the user through a sign-in and then opens nothing there while macOS shows the station's usage window.

### Controlled Boolean Controls Paint Their First Props Pass

A controlled native checkbox or switch (`AppKitControlViews.mm` on macOS, `WinUIControls.cpp` on Windows) must paint the props it is given on the **first** update after a mount or a recycle, not only when a value prop *changes*. Comparing old and new props alone leaves a control that is configured on drawn off: React mounts it with `value: true` while the component's own `_props` already hold the new value, the guard sees no change, and the row shows the opposite of the file. macOS therefore tracks `_propsApplied` (reset in `prepareForRecycle`) and every first-pass comparison is `firstPass || old != new`; Windows already treats a null `old_props` as "apply everything" (`!old_props || old != new`). When an action cannot be honoured the pane still re-mounts the control (a generation key), which re-enters the same first-pass path; the drawn state must always be able to return to the configured value.

### The Interval Loop Is What Makes The Switch Mean Something (2026-09-25)

- 同步方向 is saved from now on (`sync_direction`: `smart` | `push` | `pull`; the IPC's `sync`, an older `direction` key, and any unknown value read as `smart`).  The loop has to sync the way the field says, and a per-window picker could disagree with the background run.

### Observed Relay Read Stall Incident (2026-09-23)

- 分组管理's wheel beside 密钥 turned for seconds on every open, against an account whose reads otherwise answer in 0.25 s. A live trace of the installed app (one session probe plus one round) showed where the time goes: the session probe `GET /api/v1/auth/me` stalled 3.0 s, then the round took 5.74 s — `/v1/models` stalled twice (2.0 s, then 3.0 s) before its third attempt answered in 0.26 s, and `/api/v1/groups/rates` stalled 3.0 s — while the key, group and channel reads all answered in 0.38-0.48 s. Every stall burned the full attempt bound, because these stations fail by *answering nothing*: the TCP connection establishes (through the local TUN proxy) and then never responds, so only the socket timeout ends the read (measured with an anonymous `GET /api/status`: ESTABLISHED in `lsof`, 8 s and no byte). The account pane's mount read had already paid for the same facts seconds earlier, so opening the sheet bought a second round trip for data the window already had.
- Fix (Core): `RelayHTTPClient` gives a read its own policy. `READ_ATTEMPT_SECONDS` (`(2.0, 3.0, 4.0)`) is the bound of each attempt: a stalled read fails fast and is resent with the next bound, so one stall costs ~2 s instead of a write-sized wait, and three attempts never exceed the write bound. `RelayTransportError` marks exactly the failures a read may be resent after, stays a `RelayAccountsError`, and keeps the `Relay is unavailable` text every caller already classifies. `OPTIONAL_READ_PATHS` (`/api/user/self`, `/api/status`, `/api/v1/user/profile`, `/api/v1/auth/me`, `/api/v1/groups/rates`, `/v1/models`) answer from one `OPTIONAL_READ_TIMEOUT_SECONDS` (2) attempt with no resend: the balance, the session probe, the rate table, and a key's own gateway catalog are all summaries a stall may drop (the key keeps the model list it already had), so none of them can hold the round trip that carries the key list. Writes keep `REQUEST_TIMEOUT_SECONDS` and are never replayed; a balance read that fails keeps the last known balance instead of blanking it.
- Fix (UI): two layers. One relay read owns each account at a time — `refreshRelayResources` joins the read already in flight and reuses a read that succeeded less than `RELAY_RESOURCE_REUSE_MS` (15 s) ago, while a caller that must not see stale facts (the two host sign-in flows and the panel's own post-login read) passes `{ force: true }`; a failed read is never reused. And 分组管理 aligns over the groups Core already holds: `groupManagerHasUsableFacts` (a ready read with at least one key) decides whether the sheet reads the station at all, so opening it right after the account pane's own read never pays for a second round trip it does not need. Only an account with no usable key list still reads before it aligns.
- Known limit: the policy bounds how much a stalled connection costs, not how often the station stalls one. A round still opens one connection per read and waits for the slowest, so a station that stalls most new connections can exhaust a read's attempts. Pooling one keep-alive connection per origin — and reusing it across a round instead of opening four to five fresh ones — is the remaining structural fix for that failure shape; it is not implemented yet.
- Verified with `tests/test_core_relay_accounts.py` (`RelayReadPolicyTests`: a dropped read is sent once more, a read that stalls stops at its bound and takes the next one, a slow station is not lost with the short first bound, a write is never sent twice, a documentary read gets one short attempt, a key's gateway catalog is documentary) and `tests/test_rn_ui_parity.py` (`test_one_relay_read_serves_every_implicit_caller`, the sheet's held-facts rule, and the panel's forced post-login read) together with the focused relay, apply, IPC, and React Native contract suites, plus a temporary file trace of the installed app's own round (removed before the final build).

### Observed Proxy Idle-Timer Energy Incident (2026-09-22)

- The macOS Battery panel again listed 漾路由 under “使用大量能耗”. With the app idle (no window doing anything, no traffic) the process family — the app, Core, the proxy master and its sixteen workers — burned 2.5 s of CPU per 60 s (4.2 % of one core) with ~50 idle wakeups a second, and that is the state the app sits in for the whole of a working day.
- Cause: every proxy process ran a ten-hertz timer. Each of the sixteen workers ran uvicorn's `Server.main_loop`, which sleeps 0.1 s and calls `on_tick` purely to refresh the HTTP `Date` header once a second; the proxy master ran a 0.1 s `os.getppid()` parent check and a 0.5 s supervisor pass that health-checks all sixteen workers through the multiprocessing pipe (32 pings a second); Core ran a 0.25 s parent check. An isolated A/B of two identical sixteen-worker proxies (nothing else running, 90 s window) measured 1.83 s CPU / 8846 idle wakeups against 0.46 s / 1694 after the fix.
- Fix: `young_router/proxy_idle.py` owns both uvicorn patches and is installed from `sitecustomize.py` (interpreter startup, so the master and every worker get it before any server exists) and from `patches.install_all()`. The serve loop ticks once a second with `on_tick` still receiving uvicorn's own counter unit (ten per tick, so the `Date` header is rewritten every second exactly as before), and `Server.handle_exit` releases that wait so a stop is still honored at once — a measured stop takes 0.69 s against 1.11 s for the shipped build. `Process.is_alive` still asks the operating system about every worker on every supervisor pass and only spaces out the inter-process health check (5 s): a crashed worker is still replaced within the supervisor's own cadence, a hung one one health check later. The master's parent check and Core's parent check are now one per second, and Core's watchdog still exits at once when `stop` is set.
- Nothing on the request path changes: the tick only refreshes the header, notifies a configured parent callback, and looks for a stop, and a request is served by the event loop's I/O callbacks. Never buy idle time back by slowing a user-visible poll, delaying a view, or dropping rows — reduce what the wakeup costs instead.
- Verified with `tests/test_proxy_idle.py` (the patch replaces uvicorn's own 0.1 s tick, every tick still lands on a Date refresh, a stop signal ends the loop inside one tick, installs are idempotent, a foreign uvicorn is left alone, and the supervisor keeps per-pass liveness while spacing the ping) plus `tests/test_sitecustomize.py` (a proxy process gets all three patches and still defers the uvicorn import, a non-proxy process keeps upstream loops) and `tests/test_core_ipc.py` (Core's one-second parent check), together with the isolated A/B and the live app’s own Date freshness and shutdown timing.

### Replay Prefix, Log Memory, And Gateway Diagnosis Rules
- React Native Fabric may keep an unmounted native component in its recycle pool together with its last large props. Native tables, editors, or lists that hold bulk rows/text or derived caches must implement `prepareForRecycle` that resets `_props` to defaults and clears their AppKit backing data, columns, selection, and caches; removing the React element alone does not release that memory.
- Do not render unbounded log/trace collections with `ScrollView` plus `map`, duplicate every table cell into a data signature, or measure every cell on ordinary table updates. Virtualize long lists, memoize derived rows/columns and native props, compare old/new props directly, and reserve full content-width scans for controls whose contract requires them.
- For log-tab memory fixes, verify the installed app by repeatedly switching populated tabs and checking that RSS settles or falls after warm-up. A successful render or a single before/after sample does not disprove a retention leak.
- Treat encrypted Responses history as an immutable replay prefix. Preserve genuine `encrypted_content`, compaction items, IDs, ordering, and any image bytes inside that signed history exactly; do not recompress, re-encode, normalize, or otherwise rewrite them. Compress newly added oversized images before they enter encrypted history, and when replaying mixed history limit image compression to the suffix after the latest encrypted item.
- Do not inject `truncation=auto` or another request-control field merely because inline images in the encrypted replay prefix exceed a local image budget. Responses-compatible gateways may reject that parameter, after which route failover and stream recovery can masquerade as a long hang. Image-byte thresholds are diagnostic only; add truncation solely through the existing explicit context-size-error fallback, never preemptively from signed-prefix size, upstream 5xx, or stream timeouts.
- Large signed image history may remain in the same task while new turns are appended. To make the replay prefix smaller, accept a genuine upstream `compaction` item or start a new task; never synthesize, forge, drop, reorder, recompress, or path-rewrite signed items. Path-backed previews and image compression apply only before signing or in the mutable suffix after the latest encrypted item.
- A replayed image may be replaced by a path reference only when that path is still openable when the model later reads it: reuse a client path only for an existing non-temporary file, back every other reference with a durable copy of the same bytes, and keep the reduced inline preview when no copy can be written. Never let a path rewrite become the model's only remaining route to an image, and never advertise a path whose copy failed.
- An `encrypted_content` field containing obvious natural-language plaintext is malformed client history, not valid ciphertext. Repair only that narrow field shape back to ordinary text; do not decode, regenerate, or broadly rewrite opaque encrypted values.
- Treat signature/decryption failures such as `thinking_signature_invalid` as deterministic request errors. Return the explicit client error immediately; never send them into route cooldown or the long recovery polling loop.
- Do not infer that gateways are interchangeable merely because they may ultimately target the same upstream API. Diagnose the exact request, route, account, response event, and terminal status while keeping provider-specific workarounds out of the implementation.
- A copied, signed, or source-identical app bundle does not prove the running proxy loaded the new code. Any activation claim must show a newly started app/Core/proxy process, a healthy bound endpoint, and the unchanged configured worker count. The proxy process and its listening port are one lifecycle; do not describe a dead proxy as leaving an independently live service port.
- The native status row is an informational service-state display, not the app title or an enable/disable control. During bootstrap it must say an explicit starting state, and after localization or a Core error it must project the real running, unhealthy, stopped, or unknown state. Never leave a generic app name in that row and call it a runtime status.
- A restart is proven only when the old App/Core/proxy process group has exited and replacement processes have later start times, then the replacement proxy passes its health endpoint. A transient health-check failure while workers are booting is an intermediate startup state; only the configured stable-check threshold may produce the final running state.
- A stale desktop task status such as an earlier `systemError` is not evidence that the latest retry failed. Correlate the latest rollout turn with the proxy request record. A remote compaction is proven only by a successful request for the same task whose response contains a `compaction` item; a later successful ordinary continuation is not a substitute for that evidence.
- Do not infer a request-size limit from a structured compaction transport error or upstream 5xx. Require an explicit context-size rejection, preserve the exact upstream status instead of rewriting it to 502, and when a stream terminates without any upstream HTTP status leave the status absent rather than inventing 502. Treat prior successful compactions at comparable token counts as counterevidence to a size diagnosis.
- Deployment cooldown may remove a failed route when another eligible peer exists. It must not erase the only configured eligible deployment from a fresh request; route-recovery polls may still wait for cooldown expiry. Log pre-route failures as no available deployment or model not configured instead of the ambiguous `unselected` label.
- Keep image-size handling explicit: the service must still compress new oversized images to an accepted representation. Preserving signed historical images must not become a general exemption that allows new oversized images through unchanged.
- Responses web search is native-first. On a Responses-capable route, both an explicit native-search capability and an unknown capability must leave the original hosted-search request eligible for the upstream; never pre-inject the local `web_search`/`fetch_content` function pair because capability metadata is absent. The local pair is allowed only for an explicitly unsupported native-search capability or an already selected chat-only fallback, and after a native unsupported error only when that error is classified against the exact request and route. In any generic callback that LiteLLM rebuilds from a raw deployment, restore the selected deployment's `model_info` and surface before capability-aware adapters run. Keep focused regressions for native capability true, capability unknown, and explicit unsupported fallback, and distinguish preemptive function bridging from post-error native fallback in route traces.

## Hosted Computer-Use Requests

- The router runs no computer-use executor of its own and exposes no facade settings. A hosted Responses `computer` tool is served only by an upstream that supports it natively; every route here is a relay, so the honest outcome is the upstream's own answer or an explicit unavailability message.
- Never bridge a request that declares a hosted `computer` tool into a chat request unless the client also brings its own computer or browser tools (`_request_hosted_computer_blocks_chat_bridge`): the bridge drops the hosted declaration and would answer as if computer use had never been requested.
- Client-side computer use (Codex Desktop's `mcp__cua_repl`/`node_repl` namespace tools driving `Codex Computer Use.app`) passes through the ordinary client-tool path and needs nothing from the router.
- Codex declares those namespaces inside leading `additional_tools` input items, so every "does the client bring computer use" decision must inspect `additional_tools` as well as top-level `tools` and `tool_search_output` items (`tools._request_has_browser_computer_client_tool`); missing that made a chat-only route refuse the very client that brought its own executor.
- When a route's Responses endpoint does not exist, the bridged chat request keeps the client's computer use: namespace tools are flattened to functions carrying `x-young-router-responses-namespace` and their calls come back as `function_call` items with the `namespace` restored from the declaration or the bridged tool array. A hosted `computer` declaration with no client-side computer use is answered with `_HOSTED_COMPUTER_UNSUPPORTED_MESSAGE` before any upstream attempt rather than forwarding an invalid hosted tool to a chat endpoint.
- Verified end to end on a spare-port proxy against a fake chat-only upstream with a Codex-shaped turn (namespace in `additional_tools`): non-stream, streaming, and a second turn carrying `function_call`/`function_call_output` all restore `namespace: mcp__cua_repl`; the same turn without client-side computer use answers explicitly and makes no upstream call. - Treat a supplied Codex task/thread ID as the primary lookup key. Do not begin with repository scans, source review, or broad log searches.

- Requests-log pipeline and display rules: raw `recent-requests.jsonl` → `LogsDomain` projection (`_safe_request_record`/`_safe_recovery_record` in `young_router/core/domains/logs.py`) → TSX rendering (`renderLogRecord`/`formatLogDuration`/`formatLogTokens` in `YoungRouterApp.tsx`). Keep the cheap strip-and-reject checks ahead of `REDACT_TEXT` in `_group_service_lines` — redacting the blanks, the route trace and the banner costs ~0.5 s per refresh on its own. Unit conversions (ms→s, tokens→k) and the `sent / received` format are display-only — recording and projection stay raw integers. The projection maps `prompt/completion_tokens` to `input/output_tokens`; `_public_model_from_route_key` must capture up to the ` / name=` separator (route keys like `model=openai/gpt-5.6-sol` contain slashes) and configured public model names win over route-derived ones. LiteLLM replaces a deployment id with a per-call sha256 hash for client-side-credential and rebuilt-fallback calls, so the id alone leaves rows showing the upstream spelling (`openai/gpt-5.6-sol`) while the client called the public group (`gpt-5.6-sol`): resolve the configured name by deployment id first, then by the unambiguous route identity (`_configured_route_public_models_from`: provider + upstream model + api key name, plus order), and only when the route-derived name is just a re-spelling of the upstream model. `fitLogColumns` keeps every non-flex column at its content-sized width (timestamps, model names such as `gemini-3.1-pro`, provider, key name, status, token pairs like `148.6 / 0.7`) and gives the detail column the remainder or its floor; it never compresses fixed columns into an ellipsis, and longer values inside them ellipsize (`gemini-3.1-pro-preview` → `gemini-3.1-pro…`). The log table pairs `preserveColumnWidths` with `scrollTrailingColumnOverflow`, so the trailing detail column grows to the width its measured content needs and the table scrolls horizontally for it; the native width scan is bounded (`LiteLLMTableMeasuredRowLimit`) so a large log cannot stall a refresh. A native table that needs a scroller keeps it on screen: `updateScrollerVisibility` pins the needed scroller with auto-hide off (`applyPersistentTableScrollerChrome`) and returns to the platform chrome once the table fits again, because AppKit resets a table scroll view's initial `scrollerStyle` after the view enters a window — the init setting alone never holds, so the annotation must be re-asserted from the layout path. That scroller is the app's own translucent capsule (`LiteLLMPersistentScroller`), which can only be drawn in the legacy slot - AppKit's overlay scroller fades out while idle and a custom `NSScroller` subclass cannot take the overlay style. The legacy gutter therefore has to be removed explicitly: `FloatPersistentScrollerOverContent` (re-asserted from `LiteLLMTableScrollView.tile` and from every `InstallPersistentScrollers` call, plus `floatOverContent()` for the Swift leaf scroll views) lets the clip view span the full width and floats the scroller over the content's trailing edge. Without it a legacy bar took 15-16 pt of the pane width, squeezed a table's trailing column into an ellipsis and clipped the right frame border of a full-width table nested in a pane scroll view. The shared helpers (`installPersistentTableScrollers` in `AppKitControlViews.mm`, `InstallPersistentScrollers` and `usePersistentScrollers` for the RN pane indicator and the Swift leaf scroll views) only unhide the platform scroller and are re-run from their layout path, because AppKit rebuilds a scroller whenever a scroller flag flips back on. Every pane scroll surface is the shared `PersistentScrollView` (general, runtime, external settings, data management, route-trace timeline, provider editor and wizard): one pane must not show AppKit's overlay bar next to the persistent scroller its tables use. The pane indicator stays mounted unconditionally and measures `documentView.frame` against the clip view itself; do not gate it on a JS content measurement again (`ScrollView`'s `onContentSizeChange` plumbing left it unmounted, so panes kept AppKit's fading overlay bar while their tables showed the persistent one). Every fixed log vocabulary the viewer renders (request statuses, error reasons, log levels, menu actions) resolves through i18n; keep new tokens out of the table as raw English.
- Provider/station binding contracts (both layers, keep together): `provider.select_relay_station` is idempotent — re-binding the same station is a no-op, a binding that changes only hidden source metadata (same name, same-site URL) is cosmetic and must leave the draft clean so no discard-confirm dialog appears, and a same-site URL keeps its existing `/v1` spelling (station origins omit `/v1`). The providers workspace auto-binds custom providers whose base URL matches a station by exact host (`relay-a.example.test` ≠ `www.relay-a.example.test`), skipping name collisions, and `provider_select_relay_station` is in the revision-retryable action list.
- Codex catalog restarts: endpoint-backed repairs require two consecutive fresh observations (0.5s probe interval) before rewriting `model-catalog.json` or queuing a restart prompt; explicit enable/disable stays immediate. The post-provider-apply refresh uses the same stable gate — do not restore single-observation restarts there.
- The Codex home holds only Codex's own files plus the one managed path its `config.toml` names (`model_catalog_json` → `model-catalog.json`). This app's own catalog state never becomes a file there: the deferred-restart acknowledgement stays in Core's memory (a recreated Core re-arms it only after a real model-set or enabled-state change) and the inheritance pin is the hidden runtime setting `YOUNG_ROUTER_CATALOG_BASE_PROFILE` in the runtime settings file. Retired sidecar files in the app root or the Codex home (`model-catalog-state.json`, `young-router-…`, `litellm-menu-…`) are imported once and deleted. The model-context cache stays a shared file at `<runtime root>/model-contexts.json` because LiteLLM's worker processes read it; it is a disposable cache, not state.
- A managed catalog pointer must never be left dangling: Codex rejects its **entire** configuration (`failed to load configuration: No such file or directory (os error 2)`) while `model_catalog_json` names a missing file, so every conversation fails to resume until the pointer is fixed. A missing managed catalog is therefore rebuilt from a fresh endpoint observation even when the file (not just its content) is gone, a pointer naming either historical spelling (`young-router-model-catalog.json` from the rebrand era, `litellm-menu-model-catalog.json` from before it) counts as enabled and is migrated to the current name (file first, then the key, with the retired copy removed once the applied pointer names the current file), and a dangling pointer observed with a failed endpoint probe is dropped (restart reason `catalog_missing`) instead of leaving the client unloadable. Foreign `model_catalog_json` paths stay untouched. Repairs ride the existing snapshot paths (settings/page disk poll, Core/app start, menu open, apply) — Core deliberately has no background catalog watcher, so a deletion made with every window closed is repaired on the next poll (~3s after a settings window is opened), never silently. Every model's instructions in the catalog come from the **installed** Codex client's bundled catalog (`codex debug models --bundled`, cache keyed on the binary's mtime/size so a client update re-reads it); only a host with no Codex client at all gets this app's minimal fallback profile, and a refresh that cannot read the client's catalog while the managed file already carries the client's own instructions keeps that file (`catalog_carries_native_profile`) instead of downgrading every prompt to the fallback text. Models without a native slug inherit the client's **declared** hierarchy rather than catalog order: `select_inherited_profile` takes the visible (`visibility: list`) profile with the lowest `priority` that carries instructions, never a hidden/experimental variant. That choice is pinned as the hidden runtime setting `YOUNG_ROUTER_CATALOG_BASE_PROFILE` in the runtime settings file, so a client update that promotes a new flagship, hides a model, or reorders the catalog cannot silently re-map every third-party model's instructions; the pin is replaced only when the installed client no longer offers that profile.
- The working tree is shared: other sessions or the user may have uncommitted edits in flight (check `git status` and `git stash list` before starting; a `wip:` stash may exist). Never revert or overwrite unrelated modifications; the full test suite also contains pre-existing environment failures — attribute a full-suite failure to your change only after the failing test touches a file you modified and it reproduces in isolation.
- Focused test commands must run from the repo root: keep the `cd <repo root> &&` prefix or set the working directory explicitly. An unexpected `No module named 'tests'` (or any import error) on a previously passing command means the working directory was lost — fix the command once and rerun. Do not pipe failing output through `| tail`; tail hides the traceback head where import/cwd errors live — write full output to a temp file and grep it, or use `head -30`.

Two identical failures in a row is a hard stop: change something material (cwd, flags, output capture) or stop and diagnose from the full error. ## Public Repository Hygiene

- Do not commit runtime directories, virtual environments, package installs, generated app bundles, logs, screenshots containing real data, local traces, or WebDAV settings.
