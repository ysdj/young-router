# Young Router Repository Guide

## What Belongs Here

- This guide holds decisions a reader cannot recover from the tree: the trap, the boundary, the non-obvious consequence. Never restate what the source already states — a symbol's behaviour, a name that exists, a change that was made, or a line that was removed — because that copy drifts the moment the code moves. A rule whose whole content is "do not reintroduce what was deleted" is also pollution: the tests that fail without it are the record. Prefer a comment at the site; a rule earns a line here only when it spans files a reader would not otherwise connect.
- When an investigation finds a non-obvious protocol or lifecycle pitfall, record the observed failure mode and the invariant that prevents it in a concise comment at the owning branch before finishing the change. This rule is itself intentional and applies to later fixes.

## Scope

- `young-router` is a standalone repository; do not look for instructions in parent directories. The distribution is `young-router`, the import package `young_router`.
- Layout: `young_router/core/` (Core IPC, domains, Core-owned documents), `young_router/proxy/` (the LiteLLM data plane), `young_router/adapters/` (staged third-party workers), `young_router/config/`, `young_router/webdav/`, plus the package-root names both sides share (`callbacks.py`, `browser_identity.py`, `atomic_io.py`, `node_runtime.py`, …). `sitecustomize.py` at the repository root is copied to the Core root under the name CPython loads at interpreter startup. `rn/` is the React Native workspace (`packages/shared`, `apps/macos`, `apps/windows`), `scripts/` the build/release/update tooling, `tests/` the Python suites.
- Entry points: `python -m young_router.core|.config|.webdav` and the `young_router.core.<tool>` modules; the console scripts are named in `pyproject.toml`.
- Keep provider names, models, API keys, request IDs, local paths, traces, and logs out of committed files; `config.example.yaml` must stay publishable.

## Source Of Truth

- `rn/packages/shared/` owns the shared UI, routes, composition, interaction state, i18n, and the typed Core IPC client.
- `young_router/core/` owns domain state, validation, staged configuration, service operations, persistence, and the authenticated versioned loopback IPC contract.
- `young_router/proxy/streaming.py` is the one streaming entry point and patch surface; `streaming_recovery.py` owns route fallback, the recovery poll and its cooldowns, keepalives, and the terminal rules, and is re-exported through it.
- `rn/apps/macos/` (AppKit) and `rn/apps/windows/` (WinUI 3) own platform leaves: menus, windows, native controls, WebView hosts for the shared code panes, secure inputs, file panels, alerts, shortcuts, lifecycle.
- One feature, one shared UI, one Core domain. No second domain store, configuration writer, application shell, or legacy launcher. Embedded WebViews only for the code panes.
- React holds view state only: no config writes, no proxy process, no arbitrary paths, no raw secrets. Versioned code-editor document text is the exception.
- All user-visible shared strings go through i18n, and the language choice lives in each host's native application menu.

## Cross-Cutting Boundaries

These are the rules that span files no single comment can hold. Everything narrower belongs at the site it governs.

- Compact native density everywhere: no web-like whitespace, oversized empty cards, redundant in-content titles, or detached action rows. Tabs render only their active pane, and a compact layout reflows before controls overlap on either host.
- Labelled settings controls are fields of the one shared grid in `ui/YoungRouterApp.tsx` (`SETTINGS_FIELD_*`, `SETTINGS_PANE_INSET`, and the `SETTINGS_FIELD_*` styles). Panes spread those styles; restating the numbers or picking a pane's own inset is a regression.
- A pane that splits into a list plus a detail renders the shared `SettingsRail` and `SettingsDetailHeader` — one rail width, one row rhythm, one header height. A rail selection swaps the detail surface; it never scrolls continuously and drives the selection back.
- Every content list keeps its native frame: never drop a list's 1 pt box, because the box is how the user sees where a list ends. The settings sidebar's own source list and the `SettingsRail` are the only permitted `framed={false}`: the sidebar's box drew rules that belonged to no row over the vibrant material, and the rail is a column of its pane that already draws its own one right divider.
- A settings pane has no action footer. The shell commits as the user edits (`IMMEDIATE_APPLY_DEBOUNCE_MS`), and its one permanently mounted bottom strip is the only report surface: one status per window, never a validation card over the content, never a Core step name. The rows a failure belongs to are marked in place (`alertRowKeys`). The strip states what the user can observe, never the mechanism behind it: `revision_conflict` is this app racing itself, and every surface that can meet one already rebases once on the authoritative revision, so a conflict that still arrives reports 更改未生效 (`common.notApplied`) like any other rolled-back write — a sentence naming a second writer, or announcing what the router did about it, tells the user about a race they cannot see and cannot act on.
- A window-wide wait is a statement, never a blanket lock. Only an action the user starts in the pane that owns the button may set the counted `busy` run; every automatic write — the debounced auto-apply, the flush of a pane being left, a child surface's quiet apply, a station or model read — keeps controls enabled, because a later edit queues behind it and stages on the revision it produces. An Apply has no lock to pass at all: `applyOutcome` hard-codes `true` for that argument, so a caller cannot reintroduce the freeze by passing a flag. The failure this rule exists to prevent: leaving a pane with a staged relay draft ran its Apply under the window-wide flag, the destination pane rendered every input disabled for the length of a station-bound Apply, and the strip had already cleared to 就绪 — a live-looking window with no stated reason. Whatever still holds the controls states the wait (`处理中…` plus the app's busy wheel), and an editable field takes its own panel's pending state, never another surface's flag; a lock that persists (自动分组 owning a key name) carries its reason beside the field.
- One on/off setting is a `NativeToggle`, only a multi-select is a `NativeCheckbox`; a required field wears the `＊` at its own label.
- Field help states only what the control cannot show. It never restates the label, the value in the field, or a default the control already displays; it never announces that a value is visible ("in plain text", "明文显示") or where a control that is already on screen sits; and it never repeats a consequence the same section already states. A row whose only surviving sentence is a restatement keeps no help line at all.
- Every child surface (provider wizard, raw file editor, 分组管理, image context, sign-in browser, relay usage log, document viewer, official sign-in, model chooser) opens its own movable titled window above the window it was opened from, locked by `NativeChildPanelShield` through `presentChildPanel(_:in:prepare:)` and released by `endChildPanel`. Never `NSApp.runModal` (it freezes the React host) and never an attached sheet (undraggable, no title bar). A warm window is only created, never presented. A surface that is its own list or its own detail view is such a child surface even when a backdrop-and-card overlay would have been the shorter edit: an overlay cannot be dragged, is clipped by the pane that hosts it, and leaves the window behind it live, so it reads as a dialog the app does not honour. It gets a route the host presents as a child panel — the shared UI opens it with `native.window.open(...)`/`focus(...)` and closes it with `native.window.close(...)`, exactly like the provider wizard. Small questions inside one pane keep their documented surfaces instead: `presentDecisionPanel`/`Confirm` for a confirmation, the route's relay dialog layer for a policy picker, and the view itself for a look-at-it-full-size step.
- A child panel's lock is released on every terminal path, including a window closed while its sign-in commit is still in flight. `NativeRelayLoginController` deliberately keeps that commit alive with no window on screen, so `windowWillClose` must call `releaseChildPresentation()` itself, and the failure that settles afterwards must release again; skipping either leaves the settings window answering no click or key while it looks perfectly live, with no child on screen to explain the wait. Any new early return that bypasses `dismissPresentation()` owes the same release.
- A relay sign-in is the one-way step that asks a station to mint a session, and stations cap an account's concurrent sessions. Every path that can reach one -- Core's `restore_saved_password`, the macOS/Windows sign-in browser's remembered-password fill, and a renewal after a refused read -- asks the credential already on hand first, and only a station's own refusal (401/403 on a probe, or `AUTH_SESSION_LIMIT`) may replace it. A *rendered* sign-in form is not that refusal: a station that just accepted this browser's session may not have left `/login` yet, and a restored session that still works renders the same form while its cookies install. Waiting out a cap also has its own, much longer window than a rejected password (`YOUNG_ROUTER_RELAY_SESSION_LIMIT_BACKOFF_SECONDS`): a cap lasts as long as the sessions filling it, so retrying on the short window is what turns an unattended pane into repeated sign-in attempts, which the station reports as a blocked login.
- A child surface that writes behind its own Save/Close creates nothing before that Save, states its result beside its own footer buttons, and keeps no second status bar; the window that opened it applies quietly and says nothing about the child's work.
- Every confirmation is one decision surface per host: `AppKitNativeLeaf.presentDecisionPanel(_:message:answers:in:locksParent:completion:)` / `WinUI3NativeLeaf::Confirm`, drawn the way `NSAlert` draws one and sized from its own constants. `destructive` is stated by the caller (`hasDestructiveAction`, the system critical ink), never inferred by matching a translated label; `cancelLabel` is a per-dialog word. Return, Escape, the parent going away, and the panel's own action each answer exactly once.
- Typed IPC snapshots and actions only: never a path, a secret, or a free native capability through ordinary props. Documents flow through the versioned editor IPC under `MAX_EDITOR_DOCUMENT_BYTES` / `MAX_MESSAGE_BYTES`, and an oversized document is `editor_too_large`, not a dead Core.
- Every `@objc` export must also be declared as `RCT_EXTERN_METHOD` in `AppKitNativeLeafBridge.m`; an undeclared method is silently `undefined` in JS and an optional chain no-ops with no log.
- A new codegen component view also needs its name in `codegenConfig.ios.componentProvider` in `rn/apps/macos/package.json`. The `.mm` implementation compiles and links either way, so a missing entry is not a build error: `RCTThirdPartyComponentsProvider` simply omits the component and JS renders nothing. Adding the entry does not regenerate on its own — the codegen products under `macos/build/generated/ios` are cached, so run `pod install` there before the next build, otherwise the registry still lacks it.
- A native surface reports a wait with the app's own busy wheel (`AppKitBusySpinner` frames / WinUI `ProgressRing`), never a progress-indicator view, and the pane scroll indicator stays mounted unconditionally.
- The runtime starts from `.litellm-runtime/config.yaml`; source configuration is validated and staged explicitly, and no file mutation may silently restart the service.
- Data-plane headers stay transparent: forward a downstream header byte-for-byte, never rewrite, normalize, strip, or impersonate one, and never invent an upstream identity header. Every exception needs its own focused regression test.
- The request body has no such rule for this proxy's own containers: `extra_body` exists on the Responses wire only because `client_metadata` reaches a Responses endpoint no other way, and litellm copies that container verbatim into whatever provider body it builds. A bridge that flips the wire after the passthrough ran (`_responses_chat_bridge_retry_kwargs`, `_responses_chat_bridge_preemptive_kwargs`, the empty-retry builder, and the pre-call hook's second pass) must strip it again through `_without_responses_native_extra_body`, or an Anthropic/OpenAI validator refuses the whole turn with `extra_body: extra inputs are not permitted`. The strip is the key list, not the container: `tools` rides in the same dict for the wire being sent. And the stop that refusal produces is `_is_upstream_request_field_rejected_error` — a cause read off the field the validator named — never the unclassified branch, which told a live Codex session the router could not classify a defect this installation had built one step earlier.
- A provider validator's field refusal is the same shape whether this proxy built the field or litellm did, so that branch is `recovery` (a sibling may validate a different payload shape), and its terminal event is `invalid_request_error` + `invalid_prompt` — never a code of this router's own invention, because Codex makes every unrecognised code retryable and would loop the identical refused body.
- A Hosted tool declaration cannot cross a wire that has no such tool, but the *absence* of the declaration is not the same as the absence of search. An Anthropic surface serves Claude's own server-side search, and LiteLLM already speaks it as `web_search_options` -> `web_search_20250305`; the bridge declares it through `_with_responses_chat_bridge_provider_search` whenever the caller asked for search, which on Codex's Responses Lite lane means the `web` namespace (its `run` child is `web.run`, and its name says nothing about search, so the namespace above it is what carries the meaning). Dropping the declaration with nothing behind it is what makes a model answer from memory: observed live 2026-11-01, a `claude-opus-5-5` turn over "搜索甪直特产" made zero tool calls and invented four citation links, and the identical prompt with the declaration returned real `web_search_result` pages. Do not give this to a Chat surface: that option derives a hosted declaration this proxy has not verified.
- Releasing a provider search ahead of the answer must not overtake the reasoning that asked for it. The provider assigns `output_index` 0 to its reasoning block, 1 to the search and 2 to the answer, and a client renders in that order, so a frame inserted at the head of the queue puts the thinking below the answer it produced. `_first_answer_frame_index` inserts the search after every queued reasoning frame and before the answer's own text; a search released ahead of the whole reasoning block is the same defect in the other direction.
- A provider search that ran must reach the client before the answer it produced, and the layer that decides this is arrival order, not `output_index`. LiteLLM keeps a native `web_search` call in `provider_specific_fields['web_search_calls']` while it streams and only emits `response.web_search_call.*` at end of stream, but the answer's text deltas go into `_pending_response_events`, which the iterator drains first -- so the client rendered the whole answer above the searches it came from (four searches below the paragraph they wrote). `_release_completed_web_search_events` releases each call the moment it reports `completed` and moves the lifecycle frames to the front of the queue the iterator reads first; a call still `in_progress` is left alone, because a search that has not returned cannot be what the text was written from.
- A relay that serves `/alpha/search` and one that serves Claude's own search are different capabilities, and the second is invisible unless asked. All three `claude-opus-5-5` relays here answer `/alpha/search` with 404 ("only available for OpenAI and Composite groups"), yet two of them run `web_search_20250305` when it is declared **alone** on a clean Messages call. Declared beside the client's tools the same relay hands the declaration back as an ordinary function call and runs nothing, so a bridge that only adds `web_search_options` to the real turn still searches nothing: `search_endpoint._anthropic_search` is the clean second call that works, and it takes only the provider's `web_search_tool_result` block, never the answer prose, because that prose is where the invented URLs came from. One relay's engine also answers a place-name query with its own search documentation ten results deep, so a set sharing no term with the query is reported as no answer and the next deployment is asked rather than the model being handed a result set that only looks successful.
- A refusal handed to a model is an instruction. `search_endpoint.tips_output` used to open with "do not call web.run again, do not curl", and the model read a dead end as permission to stop working and answer from memory: the same live turn produced a long confident answer with fabricated URLs. A terminal tool answer states what failed, names the one step that still works, and says the conclusion is about the search and not about continuing the task.
- Nothing this app sends may identify it: `young_router/browser_identity.py` is the one browser identity, mirrored by `RelayBrowserIdentity` (macOS) and `kRelayBrowserUserAgent` (Windows), and a staged helper that ships its own name is normalized while it is staged. Only a loopback-only control call may keep an internal marker.
- A terminal failure names its cause, and no failure may be reported as a retry tip the client will loop on. The generic "the route failed before an answer was available" sentence is banned repo-wide and checked by `tests/test_proxy_module_integrity.py`: it covered a context-window refusal (which no resend can fix) as if it were a transport hiccup, so Codex answered by reconnecting. A cause that has a classifier gets its own branch and its own wire type (`invalid_request_error` for anything the user must change, `server_error` only for a transient route failure); the branch for an unclassified stop says so plainly and never invites the same bytes to be sent again. "Has a classifier" is a property of the exception, never of what the reader happened to see: `_synthesized_failed_response_event`'s classified branches may not be gated on `after_visible_output`, because the route-recovery poll reaches that builder with the exception that ended its window and typically before the first byte. Gating them made a `stream_start_timeout` — a cause with its own code and sentence — arrive as "the router could not classify the stop", and Pi's classifier matches nothing in that sentence, so a silent route ended a live turn for good.
- A failed turn is retried according to a per-client rule, and the router can only keep a turn alive by satisfying each one. Pi decides by **matching the rendered `<code>: <message>`** against a phrase list (`isRetryableAssistantError` in `@earendil-works/pi-ai/utils/retry.js`), so a sentence matching nothing ends the turn. That phrase list is narrower than its prose: `connection.?lost` tolerates one character, so "connection lost" matches and "connection was lost" does not, and "retry later" is not on it at all. Codex never reads the sentence: it maps `response.failed` by **exact `error.code`** (`parse_failed_response` in `codex-api/src/sse/responses_error.rs`) and then asks `CodexErr::retry_delay` (`protocol/src/error.rs`), which returns `None` only for the codes it recognises -- every other code becomes `ApiError::Retryable`. So the two obligations are mirror images on one event: a stop that cuts a turn after the route accepted it (dropped connection, half-written body, stream ended short, stall watchdog, worker restart) must carry a Pi retry phrase **and** must not use a Codex terminal code, on both `/v1/responses` and the chat-completions shape; a stop the user has to fix must carry no Pi retry phrase **and** must use a Codex terminal code (`context_length_exceeded`, `insufficient_quota`, `invalid_prompt`, ...), otherwise Codex loops over a refusal no resend can change. Two boundaries are deliberate: a cause with no Codex equivalent (`upstream_account_restricted`, the unclassified stop) stays unrecognised rather than borrowing a code that would state something false, and is bounded by the client's own retry budget -- on Pi only if its sentence also carries a truncation phrase, because a stop nobody can name has not earned a final sentence, and the shapes that reach it (a body read failing with no text of its own, a relay's `peer closed connection without sending complete message body`) are the route's transport fault, never a verdict on the bytes; and a code this router does not itself emit may not be added to `_is_young_router_terminal_failure_event`, because that set recognises *our* terminal events and an upstream sending the same code keeps its own meaning. Prove a sentence by running the client's classifier over the rendered pair and a code against its terminal set, never by reading either; `tests/test_hooks_streaming_response_events.py` pins both clients on both wire formats. The Anthropic shape is the strictest surface because it carries no error code at all, so its message alone decides: `_sanitized_upstream_route_failure_message` words its transient tail from the exception's own recovery policy, and its non-transient tails (a route's own balance or credential, a policy of `error`) must not claim a resend.
- Image context is this app's own pass and Context Attachment Manager is a wire contract, not a dependency. `young_router/proxy/image_context.py` owns which images reach the upstream, the placeholder wording and the `IMG-xxxx` ids, and it mirrors that project's text and its `selection/<thread>.json` reader; the project itself is never installed as a proxy and Codex keeps pointing at this proxy. Two consequences a reader would otherwise break: the wording is copied verbatim because the model was tuned against those exact sentences, so a "clearer" paraphrase is a different prompt, and `scripts/update_context_attachment_manager.py` re-checks the release on every artifact build and fails rather than shipping a pass that no longer matches. The fetch half is deployment-shaped: a desktop install registers `view_image_by_id` as a stdio MCP server in the client's own file, a gateway on a server has no such file and serves `POST /v1/image-context/mcp` instead (never `/mcp` — LiteLLM answers that path with its own MCP gateway, so a route added after it never matches), and `off` promises no tool at all so the placeholders ask the user. `YOUNG_ROUTER_CODEX_IMAGE_CONTEXT_FETCH` is that choice, and `auto` must keep deciding it from evidence rather than from a directory: a host that holds the client's own document *and* received the request directly may hand out a path, and the tool kind may only be named once a client has actually called the endpoint (`fetch_kind`'s `endpoint_served` marker). A gateway nothing has ever fetched from names neither -- it uses the wording this project already mirrors for a host with no tool, and the pass answers that ask itself: the next request carries every original the model's own newest message named (at most four, once), so a bare id is enough. Never put a scaled copy of a picture in a model request to make that easier: Context Attachment Manager's thumbnails are its panel's (`core/thumbnail.ts`, "scaled-down PNGs for the panel"), and the rewriter this pass mirrors states the model-side contract as a placeholder, a copy's note, or a label with nothing else changed, so a thumbnail here would be a capability this project does not have. The replay cache lives under this installation's runtime root, not in the plugin's folder. The pass rewrites only the mutable suffix of a replay — everything after the last `encrypted_content` item — because a signed prefix comes back byte-identical forever; a fetch tool that could not answer for an omitted id would leave the model holding placeholders it can never open, so `view_image_by_id` (`image_context_mcp.py`) and the replay cache in `image_context_store.py` move with it, and the switch in the runtime settings writes `[mcp_servers.young_router_image_context]` into the client's document in the same commit. That selection file's per-task `auto` switch is the plugin's own: the image-context window reads it (a tick means "every turn" exactly where the pass will omit) but never writes it, and a selection write must carry every key it does not own — rebuilding the document dropped `autoAt`/`autoSince`, which the plugin's fork and fetched-copy rules compare against. A copy the model fetches back keeps the id it names: the pass recognises one by the heading before it (`fetched_label`, in the task's own language) or by the path the file it opened carries, so a tool that answers with a line of its own — or a viewer result read as an ordinary occurrence — gives one picture two ids, and a selection made on the id the model was told stops naming that picture.
- The request log holds turns, never control-plane reads. `routing._is_local_control_plane_read` is the one predicate, and every `YoungRouterHook` terminal callback consults it before appending: `/v1/models` (a picker, `codex_config.local_exposed_models`, `claude.ClaudeDomain._public_models`) and `/health` select no deployment, so their rows carry no model, cost, or usage, and a refusal recorded for one is about this process's own startup rather than anything a person did. Observed live 2026-11-03: 707 of 982 rows were `本机网关拒绝密钥` for `/v1/models`, produced across a worker roll while the access log held zero `POST` requests — the read that produced them was this app's own client-model loop, and nothing the user did made any of them. A key a client cannot use still surfaces on the turn it sends, which is the row this log exists for; the pre-call panic path (`_record_recent_request_started`) never sees a listing at all, because a listing reaches no deployment hook.
- The macOS proxy runs with `LITELLM_NUM_WORKERS=16`. Never lower it, and never shrink it as a performance or recovery workaround.
- A restart or an install never waits for a proxy drain. Both capture the pids the bundle is running, kill them together through the one shared implementation (`scripts/app-processes.sh stop`), and start the replacement as soon as they are gone, because the loopback listener the replacement needs is released in that same instant. A signal ladder or a grace budget in that path is the wait being put back, not a gentler version of it: both clients reconnect on their own, and a turn cut there is finished after that reconnect. The four-hour `PROXY_DRAIN_GRACE_SECONDS` belongs to a replacement the Core performs on purpose, and `APP_EXIT_STOP_GRACE_SECONDS` plus the app-exit marker to the app quitting on its own through the host's quit path; `young_router/lifecycle.py` is where that split is stated, and no restart or install path may read either bound. Every managed worker therefore watches its own `process.ppid`, because that stop is `SIGKILL`: the Core is a worker's parent and a killed parent orphans its children rather than hanging them up, so a worker that outlives its Core holds its gateway and control ports until something else notices. Seventeen of them survived one install path this way.
- Every user-visible change ends by carrying it into the running app, and the fast loop is what carries it: `scripts/dev-loop-macos.sh` syncs the changed half into `/Applications/Young Router.app` and restarts once (10–16 s), which is why an edit costs the loop rather than a deploy. A change is finished when the running app carries it, not when the sources compile: a test suite, a typecheck, and a static reading of a layout are evidence about source, never about the windows the user is looking at. Running the loop is not gated on asking first — it restarts the app itself, through `scripts/restart-app.sh` — so "a restart would disturb the running app" is not a reason to skip it, and a claim about what a pane now looks like, made without it, is unverified. `YOUNG_ROUTER_MACOS_OUTPUT` is the build-only path and is for CI and release packaging.
- The deploy is a request, not the ending of every change: `scripts/build-and-install-macos.sh` re-checks the upstream releases, re-signs, and installs over `/Applications/Young Router.app`, so it runs when the user asks for a deploy or when the change cannot travel through the loop — never as the routine follow-up to an edit. Reaching a running window through `scripts/dev-loop-macos.sh` is evidence the sources are live, never that a release was deployed. A change to a native source belongs to the deploy alone — it compiles into the host executable, so the fast loop refuses it by name rather than installing a JS/Python half that no window could show, and that refusal is when the deploy is asked for.
- Every artifact-producing build first syncs `LITELLM_VERSION` to the latest installable stable LiteLLM release and re-checks each staged integration against its upstream release (`dsh-vision-router`, `Veridrop`, `dsh-connect-workbuddy`, `our-free-model`); a failed check fails the build. Resolving the release is mandatory and must stay mandatory: what a build may skip is only the *reinstall* of a release it has already staged — and only when the staged tree proves it is that exact release, by the record the staging script wrote (package, version, and the registry's published digest) plus its entry points, peers, and any staged adaptation still being intact. Anything else stages from scratch, so a stale, partial, changed, or tampered tree is never packaged. Never reimplement a staged protocol here or patch a staged package in place.
- The runtime `Core/runtime/bin` ships is not only Node. `our-free-model` moved its OpenCode free lane onto Bun and refuses that lane — the model roster included — when it finds no native `bun`, and a Finder-launched app has no login `PATH` for it to discover one on, so a host that installed Bun itself still fails from the app window. `scripts/update_bun_runtime.py` stages the platform build beside Node and `young_router.node_runtime.bundled_executable` is the only lookup; a build that ships no `bun` is a provider whose every prompt answers a transport error, which is why both artifact builds and `scripts/package-release.sh` assert it. A run-time download is never the answer here.
- Preserve LiteLLM routing, Responses stream semantics, tool ordering, ids, explicit terminal errors, and metadata-driven compatibility bridges. No request-specific or provider-specific routing hacks. A cooldown may remove a failed route only when another eligible peer exists, and it must not erase the only configured deployment from a fresh request.
- The IPC schema beside the implementation is the contract: validators, the typed client, both host bridges, and the focused tests move together. Event delivery and the shared revision are per-window contracts — one Core event stream fans out to every registered window module, and every host passes Core's private `--metadata` path so a replacement Core resumes the revision.
- Only a Core that is *gone* is replaced, never one that merely failed a request. A replacement Core stops the proxy the old one owned, and the proxy master is the process still holding the listener until a forkserver finishes preloading the runtime — so discarding Core over one timed-out or refused request destroys the start the app is waiting for, and the window that drew 启动中 has nothing left to correct it. A start asked to stop says so and releases the port instead of leaving it bound for the rest of the preload.
- The macOS Vision helper is built into `Contents/Resources/Core/bin/vision_ocr` from the RN macOS host; never restore a `Resources/App` lookup.
- An account-backed route is probed as its account, on its account's own door, and never as an empty address with a placeholder key. A row with `openai_login`/`claude_login` stores no `api_base` — its adapter owns the address — so the probe must read the session Core holds (`chatgpt_request_credential` / `token`), the `_CHATGPT_API_BASE` root, and the one surface that adapter mounts. Reading `provider.api_keys` instead reported `invalid_config` ("配置不完整") for every such route, which named a field the user had not touched and hid the real answer.
- A model roster's `client_version` is a *gate*, not this app's identity: the ChatGPT roster answers a stale claim with 200 and `{"models": []}`, which reads exactly like an account that serves nothing. It is therefore the installed client's own version (`native_codex_catalog.native_codex_client_version`), with a floor for a host that ships no client. A hard-coded version is what reported "供应商未返回模型" for an account holding five models, and `native_codex_catalog` is also where the model list itself comes from, so one module answers "what does this client say it is" and "what does it list".
- A reviewer's own environment is not evidence about another's: a failure that reproduces only in an installed bundle, only with a populated config, or only on one host is reported as such, with the boundary named.

## Diagnostics That Are Not Code Facts

Procedures a reader needs while investigating, whose subject is a log or a recorded stream rather than a function.

- Count failures by parsing each log line's `event` field, never by counting the substring `stream_idle_timeout`: it also occurs inside `deployment_failover_marked` exception text and inside `stuck` records' `body`. Copy a reproduction's own transcript to a file first, because `server.log` rolls at ~10MB and a multi-minute bridge run can straddle the rotation boundary.
- A streamed frame says exactly what it carries: empty delta fields and an empty legacy `function_call` mirror are dropped, because clients and `stream_chunk_builder` read presence as meaning. The same is true of an item's *opening*: Codex renders into the block `response.output_item.added` creates, so a route that answers a whole image generation in one read (`response.output_item.done` only, observed live 2026-11-02 on `gpt-image-2.5-flare`: a 2.2 MB PNG stored in the rollout, `task_complete` with no message, blank transcript) delivered nothing the client could draw. `image_generation._image_generation_item_opening_event` restates the missing add beside the completion it opens — never renumbering `sequence_number`, since the item was already accepted, and never twice for one item.
- Presence is the meaning on the replayed history too, and the chat bridge must not lose a field a provider reads that way. A DeepSeek thinking route answers only a history whose tool-call assistant message carries `reasoning_content` — empty is accepted, absent is a 400 — and LiteLLM's Responses-to-Chat transformation drops a `reasoning` item whose payload is only `encrypted_content` (what Codex replays), so the same conversation that answers natively on `/v1/responses` was refused after the bridge. The repair states the field as empty rather than inventing thinking: `patches._install_responses_chat_bridge_reasoning_replay_patch` runs on the one entry point that builds the bridged request, and its trace event says the replay was rewritten here.
- A list of stream events is not a list of answers. One answer arrives cut into `response.output_text.delta` frames, so reading an event list for text concatenates the frames in place; joining them like separate answers rebuilds the message one token per line. `responses_output._response_text` is that one reader, and it never reads a `function_call`'s `arguments` — that JSON belongs to the client's tool, and treating it as answer text is how a recovered tool call reached a client as an assistant message spelling out its own command character by character. Recovery that finds a polled call keeps the call and answers `None`, which its callers read as "keep the turn".

- `responses_start_buffer_released` says which frame ended the start buffer, which is the one fact that tells "this router held the thinking" apart from "the route sent it late". `released_by: response.reasoning_summary_text.delta` with `answer_started: false` means the thinking was handed over the moment it arrived, so a block that still appears all at once came from above this proxy: on a `upstream_protocol_mode: fallback` route the chat-completions stream carries reasoning progressively (watch `reasoning_content` on `/v1/chat/completions` span several seconds) while the Responses bridge in front of it emits the same frames in one burst. `answer_started: true` with `thinking_seen: false` means this side held them.
- A thinking route's frames are not the same as a thinking route's *item*. LiteLLM's Chat-to-Responses iterator builds the reasoning item from a delta carrying only `reasoning_content`, so it queues `response.output_item.added` with `id`/`type`/`status` and no `summary` array, and it never queues `response.reasoning_summary_part.added` at all. The Codex desktop app renders a summary delta only into an item that stated the summary array it fills, so on that shape the thinking never reached the block: it was drawn under the answer instead, and the stored turn kept the reasoning item while the panel showed only the message. MiniMax showed this on every turn while DeepSeek's own chat bridge (which states `summary: []` and the part frame, as `responses_execution._responses_chat_bridge_text_stream_from_chat_stream` does) rendered correctly, which is what made it look route-specific. `patches._open_reasoning_summary_items` restates the missing array and the part frame beside the item the stock iterator queues, so both paths reach the client in one shape. When a request reaches the tool adapter rather than the chat bridge, the frames are LiteLLM's, not this proxy's: prove a reasoning shape by its `output_item.added` payload, never by the presence of deltas.

- A published reasoning ladder is one ladder, and the ladder is the route's own: `published_reasoning_levels` in `young_router/core/model_contexts.py` tops every reasoning ladder out at `max` and states `ultra` beside it, and words the Pi-facing array in Pi's `off`. Neither tier is a provider claim: Codex resolves the request effort itself (`reasoning_effort_for_request` in `codex-rs/core/src/client.rs` prefers the model's `multi_agent_reasoning_effort`, then its `max`, then its highest supported non-`ultra` level — its `ultra_reasoning_uses_highest_non_ultra` test lists `ultra` on a model with no `max` and expects `xhigh` on the wire), so `ultra` does not require `max` and a route may state the top of the client's dial without serving a provider tier by that name. `proxy.reasoning` keeps a client's `max`/`ultra` clamped onto the hardest level the route maps instead of forwarding a tier no provider maps, and the Google surface folds both onto `high`. The `/v1/models` listing and the managed Codex catalog both publish through it, so a route reads the same in either client — but only if they also *resolve* it the same way. `reasoning_for` is the deployments' common surface and answers `None` when any one of a relay group resolves nothing, so a catalog that read only that kept the inherited native profile's `low`..`ultra` for a route the listing reported as `off,high,max`: one route, two ladders, and a `default_reasoning_level` the route does not have. `model_catalog._route_reasoning_capability` therefore falls back to the public name's own resolution, exactly as the request path does. An image route published more than its disabled step is the same defect one level down — the slider is a reasoning control and every extra level on it is a knob that does nothing — so `_route_is_image_model` reads the modality from the public catalog and the entry keeps `none` alone. An image route is listed in no client picker, and the filter belongs in `codex_config.local_exposed_models` because that is the one function both lists read: it is a *client* of `/v1/models`, never the server, so the router keeps publishing every route it serves and only the managed Codex catalog and the two Claude lists skip the generator — `model_catalog.route_serves_only_images` is the answer they consult. A listing entry's own `mode` names the modality when LiteLLM's cost map knows the upstream name, and the public catalogs cover the route it does not, so both signals are read. The predicate fails open on purpose (an unreadable cache answers "chat"), which means a builder that raises turns the filter into a silent no-op and puts the generator back in every picker; `tests/test_model_catalog.py` therefore drives the real lazy registry over a temporary runtime root rather than passing one in, and that test is what catches a missing import in the builder.
- A public model's context window is one number and it is resolved once, by `ModelContextRegistry.record_for` — the group's declaration, else the registry's profile. The pane's 公开上下文, the help mark's 推荐上下文 (`recommended_context_window`, which is `default_record_for`) and the managed catalog's `context_window` all read that resolution. A window an upstream *advertises* is a reading, reported in the route's own 上游上下文 row (`upstream_context_window`), and it may never stand in for the public window: it moves with every catalog read. Observed live 2026-11-04: the Our Free Model lane's capability table has no `pulse-alpha-free` entry, so the lane advertised its generic fallback 131,072 — the figure that model's card states as its *output* ceiling, against a 1,048,576 context — and the pane proposed it while the catalog written the same minute published 1,048,576; pressing 设置 would have declared the fallback on every route of the group.

## Hosted Computer-Use Requests
- The router runs no computer-use executor: a hosted Responses `computer` tool is served only by an upstream that supports it, or answered with an explicit unavailability message before any attempt.
- Never bridge a request that declares a hosted `computer` tool into a chat request unless the client brings its own computer or browser tools — the bridge would drop the declaration and answer as if it were never asked. Codex declares those namespaces inside leading `additional_tools` input items, so every "does the client bring computer use" decision inspects `additional_tools` as well as `tools`.
- When a route has no Responses endpoint, the bridged chat request keeps the client's computer use: namespace tools are flattened to functions carrying `x-young-router-responses-namespace`, and their calls come back with the namespace restored.

## Codex Task-ID Incident Triage

- A supplied task/thread ID is the primary lookup key. Do not start with repository scans or broad log searches.
- Three-hop first pass: `read_thread` on the newest 1–2 turns, the exact rollout `task_complete` event, then LiteLLM records for the same task ID in a narrow window. Keep parent-thread status, latest-turn status, and child-task status separate — a child continuing after a parent transport failure is expected.
- Prefer Codex task tools over filesystem inspection; resolve a rollout path by exact task ID from the read-only state database, never by scanning all of `~/.codex/sessions`. Query logs by exact task/request ID, event, and timestamp, printing only timestamp, event, request id, deployment, status, and a sanitized exception.
- Read source only after the exact error text or trace event names the owning branch, then stop once the causal chain is closed and make the smallest fix with its focused regression test.

## Windows Development Environment

- A checkout can be the Mac home share as seen from Windows: `C:\Mac\Home` is a symlink to the Parallels share `\\psf\Home`. Git Bash's `//Mac/Home/...` reaches Node as `\\Mac\Home\...`, and pnpm 11 then aborts with `current dir is an absolute path with drive letter`. Spell the same directory `C:\...` (or enter it through `cmd /c pushd`) for every pnpm command.
- Never install `rn/node_modules` on that share from Windows. Parallels cannot create pnpm's symlinks there: they become `.lnk` files, and `.bin` keeps an unlinkable reparse point, after which neither host resolves `react`/`react-native`. A Windows build belongs in a copy on the VM's local disk with its own `pnpm install --node-linker=hoisted`; the shared tree carries source, not a Windows module tree.
- That copy is the only tree a Windows loop can build in, and the app a Windows window shows is the AppX registration out of its `windows\YoungRouter.Package\bin\<arch>\Release` — a Release host loads `Bundle\index.windows.bundle` from its own directory. `scripts/dev-loop-windows.ps1` is the loop: it syncs the JavaScript surface from the checkout into that copy, bundles into the registered package, and restarts the app through `shell:AppsFolder`. The bundle comes from a Metro server the script keeps running, not from a one-shot `react-native bundle`: the one-shot rebuilds the whole graph and `--reset-cache` threw the transform cache away first (measured 109 s), while the server answers in 0–1 s and about 3 s after an edit — a whole run costs 13–17 s, of which 3.5 s is the restart. `-StopMetro` shuts it down, and one server per port is enforced because two sharing a cache wedge each other. The HTTP response is trimmed of its `sourceMappingURL`/`sourceURL` tail, which is the only difference from what `react-native bundle` writes; a Release host has no red box and aborts on a bundle it cannot load. `scripts/windows-ui.ps1` is how the window is read: `dump` lists every named UI Automation element with its rectangle, `click` drives one, `shot` photographs the app window alone. A native source is refused by name, because copying it would leave a window that looks updated while running the old C++; `-AllowStaleNative` is only for a JavaScript change made while native work is in progress, and the run then states which sources the window still runs from an earlier build.
- The raw-output `YoungRouter.exe` and the packaged host's own executable share one path name in two directories, and the launcher (a tiny exe that hands off to the installed MSIX) is compiled at the raw-output path after the payload copy. A second build therefore copied the launcher in as the package's app executable, and the app became a loop: launch, hand off to the AppX registration, launch again, never a window. `build-windows.ps1` writes `YoungRouter.exe.launcher` with the launcher's hash and skips that file when it copies the release tree, so the payload keeps the host the solution built.
- A machine that has never built has no `%USERPROFILE%\yr-win` and no prepared `Microsoft.ReactNative.dll`, and both used to stop it outright. The working copy is now optional: the loop debugs a checkout on the machine's own disk in place, and creates the second tree with `-InitTree` when the checkout sits behind a shared folder — detected by the reparse point on an ancestor, because Parallels mounts its share on a fixed drive that reports `Fixed` (`-Install` then installs that tree's dependencies). For the build, `-FetchPrebuilt <dir|url>` installs the prepared DLL first — verified against the digest in `rn/scripts/react-native-windows-wheel.json` and against the RNW release the tree stages, written through a temporary file so an interrupted copy cannot leave half a binary (`node rn/scripts/react-native-windows-wheel.mjs export|install|status` is that tool: export on the machine that built it, install everywhere else) — and `-AllowUpstreamWheel` (or `YOUNG_ROUTER_ALLOW_UPSTREAM_WHEEL=1`) ships the upstream wheel mapping instead of refusing: the run says so, and no claim about the wheel distance is made. Do not turn either default around — silently building in place on a share, or silently shipping the upstream wheel, are the two failures this exists to prevent.
- The architecture is spelled two ways and mixing them names a tree no build creates. Comparisons use `ARM64`/`X64`, but every path, MSBuild platform and CLI argument uses the solution configuration's platform verbatim: `ARM64` and `x64`. React Native Windows writes its own output under `target\$(Platform)\$(Configuration)` (`Directory.Build.props`), so an uppercased `X64` looked for `windows\X64\Release` and `target\X64`. `build-windows.ps1` keeps `$WindowsArch` for comparisons and `$WindowsArchName` for everything that names a directory; the wheel tool normalises the same way instead of uppercasing. Only ARM64 has a recorded `Microsoft.ReactNative.dll`, so an x64 build either builds its own or says which architecture is missing — it never silently reuses the ARM64 one.
- Two Windows facts make a scripted read look like it did nothing: Windows PowerShell 5.1 decodes a non-ASCII `-File` argument through the OEM code page, so a UI Automation element name from a Chinese UI travels as base64 of its UTF-8 bytes (`printf '%s' '运行时' | base64 -w0`); and a background process may not call `SetForegroundWindow`, so a click aimed at an unfocused app lands in whatever had focus instead. The reader attaches to the foreground thread for that reason.
- A wheel event injected into the composition island is dropped unless a synthetic mouse *move* preceded it, and these panes answer UIA `ScrollPattern.Scroll` while ignoring `SetScrollPercent`; `scripts/windows-ui.ps1` does both, which is how a settings pane is scrolled from a script at all.
- A shared `ScrollView`'s wheel step is React Native Windows' code, not this app's: `ScrollViewComponentView::OnPointerWheelChanged` hands the raw delta to the composition tracker and eases every event, which is what leaves a precision touchpad trailing the finger and coasting after release. The host links that code as the `Microsoft.ReactNative` NuGet binary by default, so an edit under `rn/node_modules` compiles nothing unless the source-build path is selected. `rn/scripts/patch-react-native-windows.mjs` maps a detent through `SPI_GETWHEELSCROLLLINES` and applies it without animation. `rn/scripts/build-windows.ps1` keeps the fast NuGet path -- a source build of RNW runs half an hour and leaves the package without a valid `Microsoft.ReactNative.pri` -- and afterwards replaces the packaged DLL with the prepared source-build output, only when both report the same file version; a machine without that incremental DLL fails before the build instead of silently shipping the upstream wheel. Verified when built by hand: the distance follows the system setting (33 px of thumb travel at 3 lines per notch, 11 at 1) and a five-detent jump lands immediately instead of over a second.
- A `tsc` run reporting hundreds of `Cannot find module 'react'` and implicit-`any` errors is the unresolved module tree above, not the source. The same commit typechecks clean in the local copy, so do not "fix" those errors in shared code.
- The `python.exe` on PATH is the Windows Store alias, not an interpreter. Run the Python suites with `uv run --no-project --with pyyaml --python 3.12 python -m unittest ...`, or with the interpreter the installed app already ships (`<install>\YoungRouter\Core\runtime\bin\python.exe -m unittest ...`), which needs no network; a `uv` that answers `invalid peer certificate: UnknownIssuer` is reading a stale `SSL_CERT_FILE`, not a broken checkout.
- This host is ARM64: `react-native run-windows` defaults to `--arch ARM64`, and an x64 build is emulated. The WinAppSDK C++/WinRT factory is `AppWindow::GetFromWindowId`; `FromWindowId` is the C# spelling and does not exist in this projection.
- The Windows secure text input is a XAML island. In this composition host its `PasswordBox` does not composite into the React surface (a debug `TextBlock` placed in the same island did not draw either). The General master key is therefore a plaintext `NativeTextField` on Windows, backed by the host's native `readSecret`/`stageSecret` capability; macOS keeps the inline secure control. That one credential is the deliberate exception to the no-secret-in-React-state rule: do not put any other secret into React state or restore the XAML leaf to the General pane.
  The same island can fault in `Microsoft.UI.Xaml.dll` when its view is unmounted; the retained-island workaround in `WinUIControls.cpp` keeps the process alive only while the view is not destroyed. A pane switch after the inline field had been mounted produced one such crash in this session, so do not put the inline secret control back on Windows without replacing the leaf.

## Development And Verification

- Keep all project-owned test sources directly under `tests/`, and keep the working tree free of `work/`, `tmp/`, and preview bundles: ephemeral probes belong in a system temporary directory that is removed when the run ends.
- A change to something the bundle ships (`young_router/`, `rn/`, a staged integration) ends with its focused checks and then `./scripts/dev-loop-macos.sh`, which carries it into the installed app and restarts once through `scripts/restart-app.sh`. A change that ships nothing — `AGENTS.md`, `README.md`, `tests/`, a staging script — is not a loop run either: no sync, and no restart of a running app. Never stop, kill, or start the app outside the loop's restart delegation and the deploy's own path, and never split a stop and a start across separate operations. `./scripts/build-and-install-macos.sh` is the deploy, and it runs on an explicit request or for a change the loop refused (a native source) — not after an edit that the loop can carry. If the mandatory PyPI sync fails on DNS or TLS, retry the same deploy in a bounded loop (with `HTTPS_PROXY`/`HTTP_PROXY` when a local proxy is needed); never bypass it.
- Decide exactly what shipped mechanically, never from the commit message: compare every source file under `young_router/` with its installed counterpart, then prove that the app, Core, and proxy processes started after that tree was written. A passing sync, build transcript, or matching version string does not prove the listener is running the files now on disk; name the installed Python file(s), new process IDs, health responses, and the exercised request paths. The RN side is judged the same way, and its minified bundle proves nothing afterwards.
- Build Windows only on a Windows host (`pnpm run build:windows`); `./scripts/package-release.sh` for a release archive. `scripts/version.py` owns `VERSION`, `BUILD_NUMBER`, and every platform's version metadata — do not add obsolete metadata back.
- A managed client catalog is generated, never hand-edited: an unknown enum value rejects the whole catalog, so verify every field against the installed client binary and regenerate through the same registry construction the Core uses.
- A managed catalog pointer must never dangle — Codex rejects its entire configuration while `model_catalog_json` names a missing file, so a deleted managed file is rebuilt, a historical spelling is migrated, and a foreign path is left alone.
- For desktop UI work a build, launch, deep link, or accessibility read is **not** visual verification: capture the target window and inspect the image, or report it unverified. `semantic`/`fused` observations can fold to an outline-only look, where a `click` target is refused and only semantic actions remain. Only a proven failure to enumerate or control the target justifies a narrowly scoped `osascript` fallback, and then read-only.
- Capture the app's own window, never a screen rectangle. `tell application "YoungRouter" to activate` fails with `-1728` (there is no application by that name), so the earlier fallback left whatever the user had in front and a `screencapture -R` then photographed that foreign window; the same trap lurks in every name lookup: the System Events process is `YoungRouter`, but the CoreGraphics window owner is the localized `漾路由`. Activate by `tell application id "young.router.app"`, read the real window id from `CGWindowListCopyWindowInfo` (a Swift one-liner through `/usr/bin/swift`; `Quartz` is not installed for the bundled Python), and capture it with `screencapture -o -l<id><path>`. A rectangle whose contents you cannot attribute to the app is an unverified read, not evidence.
- A functionality request is unfinished until that functionality has been exercised end to end against the running app in the session that claims it, with the evidence in hand — and "running" is the installed bundle carrying the change, which the loop puts there; it does not require a deploy. Source-only unit tests and direct calls into source modules do not count as end-to-end verification. Whatever could not be exercised is reported as unverified and named, never assumed to work.

## Public Repository Hygiene

- Do not commit runtime directories, virtual environments, package installs, generated bundles, logs, screenshots containing real data, local traces, or WebDAV settings. The same things do not belong in the working tree either.
- No workflow starts on its own. `push`, `pull_request`, and `schedule` are not triggers in `.github/workflows/`: a run exists only after a person dispatches one, because a commit is not a request to spend twenty minutes of runners, and an automatic red badge is not a review. What that leaves unenforced is enforced before the object exists — `scripts/check-repo-hygiene.py` runs in `pre-commit`, `commit-msg`, and `pre-push` — so a dispatched run is a second opinion, never the only one.
- `scripts/check-repo-hygiene.py` is the gate, and it runs in three places that must stay in step: `pre-commit` reads the staged blobs and the identity, `commit-msg` reads the message, and `pre-push` re-audits whole ranges, as a dispatched CI run re-audits them when one is asked for. It fails closed — an unreadable index or a missing interpreter is reported, never skipped — because a leak is not recoverable by a later commit: the blob and the object header stay reachable by id after any deletion. Install it in a fresh clone with `scripts/install-git-hooks.sh`; `core.hooksPath` lives in the clone, so a clone that skips it is still covered by `pre-push` and by a dispatched run. A false positive is reported and fixed in the pattern table, never waived with `--no-verify`.
- The tests may name a real local path under `tests/`, because proving the router does not learn one requires spelling it out; every other tracked file writes the `example` placeholder. A fixture credential is a readable word (`sk-replace-…`), never a value shaped like the real thing.
- Before every commit or push, inspect untracked files and the staged diff for credentials, private endpoints, provider/model names, request or task IDs, local paths, and copied configuration; replace real values with neutral fixtures. Passing tests does not replace this review, and neither does a green gate: the patterns cover what a machine can recognize, and a provider name pasted into a comment is not one of them.
- An upload starts by leaving nothing behind that a second upload could carry: no stash entry, no branch but the one being pushed, no worktree outside the checkout, and no stale remote-tracking ref. Inspect them (`git stash list`, `git branch -vv`, `git worktree list`, `git remote prune origin`), decide for each whether it still holds work worth keeping, and land a kept change in the commit history it belongs to rather than leaving it beside the branch. Commits `git fsck --lost-found` reports as dangling are stashes that were already dropped; recover the unique ones before the repository is pruned, and prune the rest, because a stash that survives as an unreachable commit is still a second copy of the work the push was meant to move.
- Use the intended public or noreply Git identity for public remotes. It is recorded in every clone and cannot be changed by a later commit, so it is checked before the object exists.
